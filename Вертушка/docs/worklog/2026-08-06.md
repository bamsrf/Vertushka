# Вертушка — 2026-08-06

## Свод дня

- **fix(db) — /dev/shm 512MB.** `VACUUM (ANALYZE)` на `discogs_releases_index`
  (13.1M строк) падал с «No space left on device» из-за дефолтных 64 МБ
  `/dev/shm` у контейнера БД — параллельные Postgres-воркеры держат сегменты
  именно там. Поднят `shm_size` до 512 МБ. Тем же лечится риск параллельных
  планов обычных запросов (экран артиста собирается в 3 воркера). Требует
  пересоздания контейнера БД → короткий даунтаун, не катать со срочным.

- **fix(artists) — классификация релизов, один источник правды.** Фильтр
  «Альбомы» на экране артиста тонул в интервью-дисках, radio-сэмплерах,
  микстейпах. Правила были продублированы в 3 местах (SQL-агрегаты, python,
  мобильный `matchesFilter`) и разошлись → сведены в единый
  `services/release_type.py`, дефолт «непонятное → other» (а не «→ album»).
  `bool_or` заменён плюрализмом с tie-break по специфичности (одно `Vinyl, LP`
  больше не перебивает четыре EP-версии). Замеры фильтра «Альбомы»:
  Eminem 46→16, Radiohead 52→19, Queen 169→35, Daft Punk 29→10. Сборники —
  в свой чип.
  - Побочно: `ingest_discogs_dump._derive_format` писал только ПЕРВОЕ описание
    формата → 1.06M строк без типового маркера; теперь пишутся все (таблица
    `discogs_release_formats`, 8.5M строк). Найден баг `_copy_batch` (staging
    `ON COMMIT DELETE ROWS` + asyncpg-автокоммит → COPY чистил staging до
    `INSERT ... SELECT`; `--skip-existing` молча вставлял ноль) — вероятная
    причина 13.1M релизов в индексе вместо 19.3M дампа.
