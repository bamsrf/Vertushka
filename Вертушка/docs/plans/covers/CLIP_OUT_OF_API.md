# Вынос CLIP из api-процесса

**Статус:** план (19.08.2026). Код не менялся — текущее состояние приемлемо,
но блокирует переход на 2+ uvicorn-воркера.

## Текущее состояние (что уже хорошо)

- Модель (ONNX ViT-B-32, ~350 МБ) грузится **лениво** — только при первом
  вызове визуального скана (`app/services/cover_matcher.py`, singleton
  `CoverMatcher.get()`); процесс без сканов CLIP в памяти не держит.
- Инференс и загрузка идут в `asyncio.to_thread` — event loop не блокируется.
- Фича гейтится `FEATURE_VISION_SCAN_ENABLED` и дневными квотами
  (`VISION_SCAN_DAILY_LIMIT_*`).
- Инцидент 07-10 учтён: ONNX-арены урезаны, `malloc_trim` после скана.

## Почему всё равно выносить

1000 DAU требуют 2-3 uvicorn-воркера, а каждый воркер после первого скана
резидентно держит ~350-700 МБ → OOM на 4 ГБ хосте (уже случалось с 2 воркерами).
Вынос CLIP делает память api-воркера предсказуемой (~150 МБ) и открывает
`--workers 2-3`.

## План (малой кровью, без нового сервиса)

1. **Механизм:** Redis-очередь запрос/ответ. Эндпоинт скана кладёт
   `{job_id, image_base64, candidates}` в список `clip:jobs` (LPUSH),
   ждёт результат `BLPOP clip:result:{job_id}` с таймаутом 15с
   (сейчас скан и так занимает секунды: 12 загрузок обложек + инференс).
2. **Воркер:** в scheduler-контейнере (образ тот же, модель и код уже там)
   поднять при старте `asyncio.create_task(clip_worker_loop())` под гейтом
   `IS_SCHEDULER`: BRPOP из `clip:jobs`, инференс, LPUSH результата с TTL 60с.
   mem_limit scheduler поднять 600m → 1100m (моделька + арены).
3. **Фолбэк:** если ответ не пришёл за 15с (scheduler мёртв/перегружен) —
   вернуть кандидатов без визуального переранжирования (как сейчас при
   `embed() is None`). Скан деградирует, но не падает.
4. **Затем:** `--workers 2` в docker-compose.prod.yml + slowapi и
   health_metrics на Redis + Redis pub/sub для WS-хаба
   (`services/messages_ws_hub.py` — комментарий там уже описывает как).

## Затрагиваемые файлы

- `app/services/cover_matcher.py` — разделить на клиент (очередь) и воркер.
- `app/api/records.py:_visual_rerank` — ходить через клиента.
- `app/main.py` — старт воркер-лупа под `IS_SCHEDULER`.
- `docker-compose.prod.yml` — mem_limit scheduler; позже workers api.
