# Milestone: обложки на S3 + imgproxy + вынос CLIP

> Статус: **АКТИВИРОВАН 2026-08-27** (цель владельца: готовность к 1000 DAU,
> обложки молниеносно; вдобавок 90% зеркал защищены от LRU и ядро перерастает
> диск — см. COVERS_STRATEGY.md, ревизия 27.08). Подготовка трека A уже в коде:
> dual-write зеркала в S3 за флагом `COVERS_S3_ENABLED` (app/services/s3_covers.py,
> хук в _encode_and_place) + реконсилер/миграция app/scripts/sync_covers_to_s3.py.
> Железо: RAM уже 4 ГБ (скрин панели 27.08) — предусловие ниже выполнено,
> тариф не трогать. Осталось: бакет у провайдера (решение владельца) →
> миграция → флаг → read-путь imgproxy/S3 + снятие LRU-защит.
> На момент составления: ~10 юзеров, pre-launch, VPS 2 ГБ/2 ядра сознательно
> оставлен как есть. При такой нагрузке ни одно горлышко не болит, лифт
> преждевремен. Execution-версия архитектуры из
> [COVERS_ARCHITECTURE_NORMALIZATION.md](COVERS_ARCHITECTURE_NORMALIZATION.md).
> Цель (когда придёт время): убрать два структурных потолка перед ростом —
> «диск-стена под обложки» и «один API-воркер».

## Когда это делать — триггеры

Не по календарю, а по сигналам. Инструменты замера уже есть
(`cover_coverage_tasks`, `health_metrics`, `/health/covers`). Пора начинать,
когда сработал ЛЮБОЙ:

- **Перед выходом в стор** с маркетинговым пушем — не после того, как легло.
- **Диск:** свободно на `/dev/vda1` стабильно < 5 ГБ, ЛИБО растёт доля
  cache-miss обложек (серые квадраты после LRU-эвикции) → трек A.
- **Память:** свободно RAM регулярно < ~150 МБ ЛИБО autoheal-рестарты API
  участились → сначала VPS 4 ГБ, следом трек B.
- **Латентность:** `health_metrics` p99 ползёт под нагрузкой ЛИБО регулярно
  > ~50 одновременных → трек B (2-й воркер, после выноса CLIP).
- **Discogs:** волна TimeoutError в acquire() (очередь глубже ~28) — но это
  самолечится прогревом, проверять в последнюю очередь.

До тех пор — ничего из нижеследующего не трогать.

## Железо (предусловие)

- VPS → **4 ГБ RAM / 40 ГБ NVMe / 2 ядра**. +2 ГБ снимают память-потолок:
  освобождают бюджет под контейнер CLIP + imgproxy + 2-й API-воркер.
- 2 ядра остаются → реалистичный максимум **2 API-воркера** (1/ядро). Для
  1000 DAU достаточно: тяжёлый CPU (CLIP, ресайз) уходит из воркеров, остаток
  I/O-bound. 4-ядерный тариф — позже, когда перерастём.
- GlitchTip живёт на этой же машине (~500-600 МБ). Кандидат №1 на вынос
  off-box, если память снова станет тесной. Вне скоупа этого milestone.

## Два трека, склеены намеренно

Вынос CLIP освобождает память → **можно** добавить воркеров.
imgproxy уводит ресайз из Python → воркерам **нечем** больше тормозить.
По отдельности — половина эффекта. Порядок: сначала S3+imgproxy (обложки
перестают быть работой сервера), потом CLIP+воркеры (масштаб по CPU).

## Трек A — S3 + imgproxy + proxy_cache

### A0. Провайдер object storage (РЕШЕНИЕ, блокирует A1+)

S3-совместимый bucket, **со-локация с VPS** (та же площадка = минимальная
задержка + бесплатный/дешёвый egress между compute и storage). РФ-хостинг
обязателен — вся мотивация в уходе от медленного из РФ Discogs CDN.
Кандидаты: Selectel / Yandex Object Storage / VK Cloud. Endpoint + ключи →
в `.env.prod` (никогда в git).

### A1. Storage-абстракция (провайдер-агностична, S3 API одинаков)

- Новый `app/services/cover_object_store.py`: интерфейс `put_master(id, bytes)`,
  `master_url(id)`. Backend — `aiobotocore` (async S3), endpoint/bucket/creds
  из config. Fallback-флаг `COVER_STORE_BACKEND=local|s3` — переключаемся без
  переписывания вызовов.
- Config: `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`,
  `S3_REGION`, `COVER_STORE_BACKEND`.

### A2. cover_storage → пишет мастер в bucket, не на диск

- `_encode_and_place` (уже вынесен в threadpool) остаётся для нарезки, но
  назначение — bucket через A1. Локальный путь сохраняется под флагом на
  переходный период.
- Мастер = максимальное качество, ОДИН размер. Нарезку делает imgproxy.

### A3. imgproxy — контейнер рядом с nginx

- Сервис в `docker-compose.prod.yml`: образ `darthsim/imgproxy`, ~20-30 МБ RAM.
- `IMGPROXY_KEY`/`IMGPROXY_SALT` — подпись URL (как у Discogs: защита от
  ресайз-абуза). Источник — S3 bucket (`s3://` или presigned).
- Формат-негоциация ON: WebP/AVIF по `Accept` (−~30% веса; у Discogs выключено).

### A4. nginx — proxy_cache деривативов

- `proxy_cache_path /var/cache/nginx/covers max_size=<N>g inactive=30d` —
  **капнутый и самоочищающийся** кэш нарезок (замена нынешнему LRU-трэшу).
- `location /covers/` → imgproxy upstream, с сохранением текущего `try_files`
  fallback на переходный период. HTTP/2 / sendfile / expires уже есть.

### A5. Mobile — размер под уровень зума

- Сетка запрашивает `?w=200`, деталь `?w=1000`. Мерцание L3↔L4 лечится
  disk-кэшем expo-image + `recyclingKey` (уже есть), не «один URL на все».
- Обновить docstring [ZoomableRecordGrid.tsx:23] — сейчас врёт про «L4+ thumb».

### A6. Миграция существующих 13K мастеров

- Одноразовый скрипт: залить текущие `uploads/covers/*.jpg` (~1.1 ГБ) в bucket.
- Затем переключить `COVER_STORE_BACKEND=s3`, `public_covers_base` → imgproxy.
- Локальный volume — резерв на переходный период, потом снять.

## Трек B — CLIP в отдельный контейнер

### B1. CLIP-сервис

- Вынести `cover_matcher.py` (ONNX-инференс) в отдельный сервис/контейнер.
  Контракт: HTTP (`POST /embed` → вектор) либо общий volume под модель.
- Своя память (~450 МБ), свой рестарт. API-воркер больше НЕ грузит модель.

### B2. API → 2 воркера

- `docker-compose.prod.yml`: `--workers 1` → `--workers 2`. Возможно только
  после B1 (без CLIP воркер ~200 МБ, 2×200 влезает в 4 ГБ).
- Пересчитать пороги `health_metrics` (окно станет пер-процессным — коммент
  в services/health_metrics.py это уже предупреждает).
- БД-пул уже безопасен (10+15=25/процесс, 3 процесса × 25 = 75 < 100).

## Порядок исполнения

1. **A0** — выбрать провайдера (блокирует всё в треке A).
2. **A1 → A2** — storage-seam + запись мастеров (флаг `local`, поведение не
   меняется, готовим переключатель).
3. **A3 → A4** — imgproxy + nginx-кэш (трафик ещё по-старому, fallback жив).
4. **A6** — залить мастера, переключить флаг на `s3`. Обложки на новом тракте.
5. **A5** — Mobile размеры под зум (после того как imgproxy отвечает).
6. **B1 → B2** — вынос CLIP, второй воркер.

Каждый шаг обратим: флаг `COVER_STORE_BACKEND` и nginx `try_files` fallback
держат старый путь живым до подтверждения нового. Даунтайма нет.

## Что НЕ трогаем

- Discogs token-bucket / приоритетную очередь — не горлышко.
- Цепочку прогрева CAA→barcode→Discogs→iTunes — меняется только куда кладём
  результат (bucket вместо диска).
- Метрику покрытия (`cover_coverage_tasks`) — уже есть, будет мерить эффект.
