# Правила разграничения правок iOS ↔ Android

> Статус: действующее правило. Источник правды для любых правок в `Mobile/`.
> Появилось после серии «починили на Android — сломали на iOS» (PR #231 → #241 → #253).

## 0. Зачем

Проект — один кодовый ствол на две платформы. Большая часть UI-кода общая,
поэтому правка, задуманная как «только для Android», по умолчанию **уезжает и в
iOS**. Обратное тоже верно. Живой пример, на котором это правило и выросло:

| PR | Что сделали | Что сломали |
|---|---|---|
| #231 | на Android поджали плейсхолдер поиска через `numberOfLines={1}` с пометкой «на iOS инертен» | RN прокидывает проп в обе ветки и **меряет им инпут** — на iOS текст уехал на ~9pt вниз |
| #241 | починили iOS | |
| #253 | тот же симптом всплыл в поиске Маркета | |

Вывод: «на другой платформе это ничего не делает» — гипотеза, а не факт. Её
нужно либо доказать, либо обнести явным guard'ом.

---

## 1. Три корзины. Классифицируй ДО первой правки

Любая задача по мобилке кладётся ровно в одну корзину, и это пишется в первой
строке описания PR:

- **`platform: ios`** — меняется только iOS-поведение. Android-рендер обязан
  остаться бит-в-бит прежним.
- **`platform: android`** — зеркально.
- **`platform: both`** — общая правка. Тогда обе платформы проверяются и обе
  упоминаются в описании: «на iOS X, на Android Y».

Запрещённая формулировка: «правка для Android, iOS не трогаем» — если файл
общий и guard'а нет. Это либо `both`, либо нужен guard (раздел 3).

Если в ходе работы корзина меняется (начали как `android`, выяснилось, что
задевает общий компонент) — корзина переписывается в PR, и добавляется проверка
второй платформы. Молча оставаться в старой корзине нельзя.

## 2. Где проходит граница: выбор механизма

По возрастанию «жёсткости» разделения. Бери самый лёгкий, который достаточен.

### 2.1. Токен / одно значение → `Platform.select`

```ts
gap: Platform.select({ android: 8, default: 10 }),
```

Годится для отступов, шрифтовых поправок, теней. Всегда через `default`, а не
через `ios:`/`android:` по отдельности — иначе третья платформа (web) получает
`undefined` и стиль молча пропадает.

### 2.2. Проп компонента → явная ветка, а не «инертный» проп

**Никогда** не полагайся на то, что проп «на другой платформе ничего не делает».
Прокидывай его условно:

```ts
const androidOnlyProps = Platform.OS === 'android' ? ({ numberOfLines: 1 } as const) : ({} as const);
<TextInput {...androidOnlyProps} />
```

Это ровно тот паттерн, который уже стоит в `app/(tabs)/search.tsx:168`. Если
видишь голый «Android-only» проп в общем JSX — это дефект, даже если сейчас он
не проявляется.

### 2.3. Расходится вёрстка или жест → отдельный файл `.ios.tsx` / `.android.tsx`

Порог: **больше трёх `Platform.OS` в одном компоненте** или расхождение в
структуре дерева (а не в числах) → раздели файлы. Metro сам подставит нужный.
Общая логика выносится в platform-agnostic хук/модуль рядом.

### 2.4. Целая фича одной платформы → отдельный модуль с говорящим именем

Как уже сделано: `components/AndroidEdgeSwipeBack.tsx`, `lib/useAndroidOverdrag.ts`,
`lib/useAndroidBackClose.ts`. Хук сам возвращает пустышку на чужой платформе
(`if (!IS_ANDROID) return {}`) — вызывающий код остаётся общим и чистым.

Это предпочтительный способ для всего нового Android-only: правка физически не
может дотянуться до iOS.

## 3. Правило guard'а (главное)

> Любая правка в **общем** файле, мотивированная поведением одной платформы,
> либо обнесена явной проверкой `Platform.OS`, либо признана `both` и проверена
> на обеих.

Третьего не дано. Комментарий `// только для Android` guard'ом **не является**.

Проверка перед коммитом: открой diff и на каждый изменённый hunk ответь —
«что этот hunk делает на второй платформе?». Ответ «ничего» принимается только
если hunk физически недостижим на ней (guard, `.android.tsx`, Android-only модуль).

## 4. Проверка: что чем покрыто

Важный факт про текущий стенд: **jest настроен только на iOS** —
`"preset": "jest-expo/ios"` в `Mobile/package.json`. То есть:

- снапшоты `__tests__/*.ios.test.tsx` + `__snapshots__/*.snap.ios` сторожат
  **только iOS-рендер**;
- Android-рендер автотестами **не покрыт вообще**;
- platform-agnostic логика (`androidOverdrag.test.ts`, `edgeSwipeBack.test.ts`,
  `responsive.test.ts`) тестируется как чистые функции — это и есть рабочий
  способ покрыть Android.

Отсюда матрица обязательных проверок:

| Корзина | Обязательно |
|---|---|
| `ios` | `npm test` (снапшоты iOS зелёные и **изменились осознанно**) + визуально симулятор |
| `android` | вынести логику в чистую функцию и покрыть unit-тестом; `npm test` должен остаться **без изменений снапшотов** — если iOS-снапшот дрогнул, правка не Android-only |
| `both` | и то, и другое + визуально обе платформы |

`npm test` и `npm run typecheck` — до PR, всегда. После апгрейда SDK — tsc
в первую очередь (см. `SDK_UPGRADE_CHECKLIST.md`).

**Ключевой индикатор:** изменившийся iOS-снапшот в PR, помеченном `platform: android`,
— это стоп-сигнал, а не «ну обновлю baseline». Разбирайся, почему дотянулось.

Перед крупной Android-правкой в общем компоненте полезно сначала **завести
iOS-снапшот-гейт** на этот компонент отдельным коммитом — так уже делали
(`16137a2 test(ios): снапшот-гейт RecordGrid и MarketMain перед Android-overdrag'ом`).
Это лучший приём из имеющихся: гейт ставится до правки и ловит утечку сразу.

## 5. Нативный конфиг и сборка

`app.config.js`, `app.json`, config-плагины, зависимости — **общие для обеих
платформ по определению**. Любая их правка это минимум `platform: both` по
рискам, даже если цель — одна платформа.

- iOS защищён гейтом `Mobile/ci/check-ios-baseline.sh`: чистый `expo prebuild -p ios`
  сравнивается с `ci/ios-baseline/`. Если правка «для Android» валит этот гейт —
  она не Android-only.
- Осознанное изменение iOS-конфига: `bash ci/update-ios-baseline.sh`, diff в PR,
  метка `ios-config-change`.
- Android-эквивалента baseline-гейта нет → Android-конфиг проверяется руками
  (`expo prebuild -p android --no-install --clean` + глазами по diff'у).
- Platform-specific поля конфига класть в `ios: {}` / `android: {}`, а не в корень.

## 6. Именование: чтобы платформа читалась из истории

Уже сложившаяся и обязательная к продолжению конвенция:

- Ветки: `fix/android-<что>`, `fix/ios-<что>`, общее — `fix/<область>-<что>`.
- Коммиты: `fix(android): …`, `fix(ios): …`, `feat(android): …`.
  Для общих — доменный scope (`fix(search): …`, `fix(market): …`) и **обе
  платформы упомянуты в теле**.
- Если правка одной платформы намеренно не задевает вторую — так и пишем в теле:
  «iOS не меняется» (как в `2f9a414`). Это фиксирует намерение и делает будущий
  регресс доказуемым.

## 7. Выкатка: OTA-каналы разные

Каналы разведены: `update:prod:ios` → `production`, `update:prod:android` →
`production-android`, `update:preview:android` → `preview-android`.

Правило: **общая правка (`both`) выкатывается в оба канала**. Выкатить `both`
только в Android-канал — это создать расхождение, которое потом диагностируется
как «баг на iOS». Правка `android` — только в Android-канал, и наоборот.

Отдельно: у владельца preview-APK на реальном телефоне — доставка правок туда
**только** через `update:preview:android`, APK не пересобирать.

## 8. Известные точки сцепления

Места, где «одна платформа» исторически протекала в другую. При правке любого из
них — автоматически режим `both` по проверке, даже если цель одна платформа.

| Точка | Чем сцеплено |
|---|---|
| Поиск: плейсхолдер/высота инпута (`app/(tabs)/search.tsx`, `components/market/MarketMain.tsx`) | `numberOfLines` участвует в измерении на обеих; сторожит `__tests__/marketSearchPlaceholder.test.tsx` |
| Компактные шрифты / `responsive` (`constants/theme.ts`, `lib/responsive.ts`) | boost кегля задумывался под iOS, ломал вёрстку 360dp на Android (`21ba695`) |
| Таб-бар (`components/ui/GlassTabBar`) | стекло/высота + safe-area; есть iOS-снапшот |
| Сетки и карточки (`RecordGrid`, `AutoRail`) | `includeFontPadding`, gap'ы, тени |
| Шторки (`OptionsSheet`, `PromptSheet`, `RootOverlay`) | инсеты и поведение back-жеста |
| Overdrag / свайп назад | Android-only по реализации, но живёт поверх общих экранов |
| Сплеш и интро | `app.config.js` общий, размеры логотипа платформенные |

Список пополняется: поймал новую утечку — допиши строку в этой таблице тем же PR.

## 9. Если ping-pong уже случился

1. Найти коммит, который внёс сломавшую правку: `git log -S '<кусок кода>' -- <файл>`.
2. Прочитать, **какая корзина** была заявлена. Почти всегда правка была
   заявлена как одноплатформенная без guard'а.
3. Чинить не «подкруткой числа под вторую платформу», а восстановлением границы:
   поставить guard / развести файлы. Подкрутка числа даёт третий раунд.
4. Закрыть тестом на инвариант, а не на пиксель (пример — `marketSearchPlaceholder.test.tsx`
   сторожит «высота задана явно» и «`numberOfLines` не уходит на iOS»).
5. Дописать строку в таблицу раздела 8.

## 10. Чек-лист PR по мобилке

- [ ] В описании первой строкой: `platform: ios` / `android` / `both`
- [ ] Каждый hunk в общем файле: либо под guard'ом, либо осознанно `both`
- [ ] Нет «инертных» пропов без проверки платформы
- [ ] `npm run typecheck` зелёный
- [ ] `npm test` зелёный; снапшоты iOS изменились **только** если корзина `ios`/`both`
- [ ] Android-логика покрыта unit-тестом на чистой функции (если корзина `android`/`both`)
- [ ] Трогал `app.config.js` / плагины / зависимости → прогнал `ci/check-ios-baseline.sh`
- [ ] Затронута точка из раздела 8 → проверены обе платформы
- [ ] Имя ветки и scope коммита отражают платформу
- [ ] Выкатка в тот канал (или каналы), которому соответствует корзина
