# Обложки: нормализация архитектуры под масштаб

> Статус: черновик плана (2026-08-04). Основан на замерах прода + реверсе
> инфраструктуры Discogs. Заменяет допущение «зеркало на локальном диске»
> из [COVERS_RATE_LIMIT_STRATEGY.md](COVERS_RATE_LIMIT_STRATEGY.md).

## TL;DR

Discogs rate-limit (60/min) — **не** горлышко: он самолечится прогревом,
нагрузка пропорциональна числу уникальных холодных релизов, а не числу юзеров.
Реальное горлышко — **локальный диск под зеркало**. Нормализация = повторить
схему Discogs: один мастер в объектном хранилище + деривативы на лету + CDN-кэш.

## Замеры (прод, 2026-08-04)

| Метрика | Значение |
|---|---|
| Диск `/dev/vda1` | 29 GB, занято 21 GB, свободно 7.2 GB (75%) |
| Обложек на диске | 13 102 файла = 1.1 GB (~84 KB/шт) |
| Хранимых размеров | 1 (1000px, q85) |
| Дамп-индекс `discogs_releases_index` | 13 120 056 строк |
| Из них с `cover_image_url` | 1 650 491 (12.6%) |
| Реально зеркалировано (`records.cover_local_path`) | 10 905 (0.08%) |
| drip-воркер | до 25/мин при tokens>25 ≈ 86K/сутки ≈ 3 GB/сутки |

**Вывод по объёму:** зеркало известных 1.65M URL = ~138 GB. Полный каталог
16M = ~1.34 TB. Свободно 7.2 GB. Локальный диск не масштабируется в принципе;
при активном drip свободное место кончается за ~2 суток, унося за собой
Postgres (тот же раздел).

## Как это устроено у Discogs (реверс по боевым URL)

```
https://i.discogs.com/<HMAC>/rs:fit/g:sm/q:90/h:595/w:600/<base64(s3-путь)>.jpeg
```

- Хвост = `base64("s3://discogs-database-images/R-<id>-<ts>-<n>.jpeg")` —
  **один мастер-файл** на изображение.
- Все размеры (`w`, `h`, `q`) вычисляются **на лету** сервисом imgproxy.
- Путь подписан HMAC: подмена `w:600`→`w:150` даёт **HTTP 403**.
- `server: cloudflare`, `cf-cache-status: HIT`, `max-age=31536000` —
  деривативы живут в CDN год, origin трогается раз в год на размер.
- Формат-негоциация **выключена**: на `Accept: image/webp` отдаётся `image/jpeg`
  (они теряют ~30% — здесь мы можем их обогнать).

Сжатие у нас не хуже: их 600px/q90 = 95 KB, наш 1000px/q85 = 84 KB. Проблема
не в компрессии, а в том, что мы храним один размер и возим его и на детальный
экран, и на ноготь в сетке 10 колонок (перерасход ~73× по площади).

## Целевая архитектура

```
                       ┌─ CAA / MusicBrainz / iTunes / Discogs (прогрев, как есть)
                       ▼
   [мастер] ──────► Object Storage (S3-совм.)     ← платим за факт. GB, не за стену
   1000px+ q90        s3://vertushka-covers/{discogs_id}.jpg
                       │
                       ▼
   Mobile ──► nginx ──► imgproxy ──► дериватив на лету (w=200 / 500 / 1000, webp по Accept)
                 │          ▲
                 └─ proxy_cache (max_size=N GB, inactive=30d) ── ограниченный, самоочищаемый
```

### Компоненты

1. **Object Storage (S3-совместимое).** Selectel / VK Cloud / Yandex Object
   Storage. Хранит **только мастера** (1 размер, максимальное качество).
   Стены в 7.2 GB больше нет — платёж линеен по фактическому объёму.
   Прогрев становится ленивым и бюджетно-предсказуемым.

2. **imgproxy (контейнер рядом с nginx).** Go, ~20 MB RAM, влезает в текущие
   лимиты. `/covers/{id}?w=200` для сетки, `?w=1000` для детали. Ресайз
   уезжает из Python-процесса → пункт «блокирующий Pillow» закрывается сам.
   Подпись URL включить (как у Discogs) — защита от ресайз-абуза.

3. **nginx proxy_cache.** Кэширует деривативы с длинным `expires`, как
   Cloudflare у Discogs. `proxy_cache_path max_size=<N>GB inactive=30d` —
   диск под кэш **ограничен сверху и самоочищается**, не растёт бесконтрольно.
   HTTP/2 / sendfile / try_files уже настроены корректно — не трогаем.

4. **Формат-негоциация ON.** imgproxy отдаёт WebP/AVIF по `Accept`. У Discogs
   выключено — наш выигрыш ~30% трафика поверх их схемы.

### Mobile

- Вернуть выбор размера по уровню зума (docstring [ZoomableRecordGrid.tsx:23]
  утверждает «на L4+ thumb», код это не делает — оптимизация снята, коммент
  забыт). С imgproxy: сетка запрашивает `?w=200`, деталь `?w=1000`.
- Мерцание L3↔L4 при смене source лечится не «один URL на все уровни», а
  disk-кэшем expo-image + фиксированным `recyclingKey` (уже есть).

## Миграция (без даунтайма)

1. Поднять bucket + imgproxy-контейнер + `proxy_cache_path`. Трафик пока идёт
   по-старому.
2. Роут `/covers/` → imgproxy с fallback на текущий `try_files` (старые файлы
   на диске продолжают отдаваться, пока не перельём).
3. Фоновая заливка существующих 13K мастеров в bucket (одноразово, ~1.1 GB).
4. Переключить `cover_storage` на запись мастера в bucket вместо диска.
5. `public_covers_base` → imgproxy-эндпоинт. Старый локальный путь — как
   резерв на переходный период, потом убрать volume.

## Побочные правки (независимы, делать сразу)

- **`_thumb_to_cover` ([discogs.py:287]) — мёртвый код.** Regex
  `_\d+\.(jpg|jpeg|png)` — схема старого CDN; в нынешних `i.discogs.com` URL
  не матчится, функция возвращает вход как есть. Docstring врёт. Удалить или
  переписать под реальность.
- **Pillow → `asyncio.to_thread`** в `cover_storage.py` (~141, ~186, ~377) —
  актуально до миграции на imgproxy как быстрый митигейт блокировки event loop.
- **DB pool** ([database.py:18]) — комментарий «×4 воркера» устарел
  (реально `--workers 1`). Поднять `pool_size` 5→10-15, запас по
  `max_connections=100` есть.
- **CLIP в отдельный контейнер** — развязывает `--workers 1` (CLIP ONNX
  ~350 MB резидентно ⇒ 2 воркера = OOM). После выноса API масштабируется
  горизонтально.
- **Метрика покрытия обложек + алерт** — п.4.2 из
  [MARKET_COVERS_AND_INGEST_FIX.md]. Без неё % покрытия каждый раз снимается
  руками с прода.

## Что НЕ трогаем

- Discogs token-bucket / приоритетная очередь ([rate_limiter.py]) — работает,
  горлышком не является.
- Цепочку прогрева CAA→barcode→Discogs→iTunes — источники мастеров корректны,
  меняется только куда кладём результат (bucket вместо диска).
- nginx HTTP/2 / sendfile / expires — настроены правильно.
