## 1. Метрика

Считаем не магазины, а **HTTP-запросы, помещающиеся в ночное окно**.

Базовая единица из кода: `rate_limit_per_sec = 0.5` у всех парсеров
([base.py:83](../../Backend/app/services/scrapers/base.py), переопределён в каждом shop-файле)
→ **1 запрос = 2 секунды слота магазина**.

### Два уровня ограничения

**Потолок одного магазина** — 1800 запросов/час. Лимит стоит per-domain
(`http_client.configure_domain()` в [runner.py:52](../../Backend/app/services/scrapers/runner.py)),
поэтому магазины **не отъедают квоту друг у друга**: седьмой магазин не замедляет первые шесть.

**Глобальный потолок** — `SCRAPER_CONCURRENCY = 5`
([scraper_tasks.py:40](../../Backend/app/tasks/scraper_tasks.py)). Одновременно крутится 5 магазинов,
поэтому бюджет измеряется в **стор-часах**:

```
окно full-HTTP: 02:00 (daily_market_sync) → 05:00 (enrich_artist_data) = 3 ч
3 ч × 5 слотов = 15 стор-часов ≈ 27 000 запросов за ночь
```

Плюс дневной `incremental_market_sync` в 14:00 — окно шире, но конкурирует с живым API-трафиком.

**27 000 запросов за ночь — бюджет, который делим между магазинами.**

## 3. Главная проблема: «ежедневный сток» — не совсем правда

Наличие обновляет не crawl, а `stock_refresh_active`
([scraper_tasks.py:157](../../Backend/app/tasks/scraper_tasks.py)):

- `per_store_limit = 200`, `interval hours=6` → **800 листингов на магазин в сутки**;
- берутся только `matched_record_id IS NOT NULL` + `status = IN_STOCK` + `requires_browser = false`.

Следствие: полный цикл проверки наличия =

| matched-листингов в магазине | цикл обновления стока |
|---|---|
| ≤ 800 | 1 день ✅ |
| 2 000 | 2.5 дня |
| 5 000 | **6+ дней** ❌ |

То есть обещание в UI выполняется только для небольших магазинов. Это надо чинить **до**
расширения списка, иначе деградирует у всех сразу.

## 4. Стратегия отбора: чек-лист на 10 минут

Проверять по порядку, останавливаться на первом «да». **Размер каталога почти не важен —
важен способ доступа.**

1. **YML / Yandex-Market фид** — `/yandex_market.xml`, `/yml.xml`, `/export/`.
   Весь каталог с ценой и наличием одним файлом. У Bitrix-магазинов есть почти всегда. Джекпот.
2. **JSON-каталог CMS** — Tilda (`/store/api/…`), InSales, Shopify (`/products.json`). Как `found`.
3. **AJAX-эндпоинт пагинации** — открыть каталог, посмотреть Network при скролле. Как `stoprobotvinyl`.
4. **Листинг-страницы, где в карточке есть цена И наличие** — 5000 SKU при 48 на страницу
   = **~100 запросов** вместо 5000.
5. **Только sitemap + страница на товар** — дорого. Брать, если каталог < 3000 и магазин ценный.
6. **`requires_browser`** — самый дорогой класс (weekly full). Максимум 2–3 штуки, только за
   уникальный сток.

## 5. Тиринг и ёмкость

Раздаём магазинам **бюджет запросов в сутки**, а не место в списке.

| Tier | Стоимость/сутки | Ёмкость | Что ограничивает |
|---|---|---|---|
| **A** — фид / JSON / AJAX | 1–100 запросов | **30–50** | матчинг и БД, не сеть |
| **B** — листинг-страницы | 100–1000 запросов | **10–15** | ночное окно |
| **C** — страница на товар | тысячи | **3–5** | ночное окно, целиком |
| **D** — `requires_browser` | weekly full | **2–3** | CPU браузерного пула |

**Сегодня безопасно:** 10–15 магазинов при текущем перекосе в Tier C.
**После работ из §6:** 40–60, из них большинство — Tier A.

### WS1.7 — Устойчивость обхода (✅ 2026-08-11)

Ночь 08-11 прошла за **24 минуты** (02:00→02:24, 38 609 позиций, 7 магазинов) —
бюджет ночного окна занят на 13%. Но два магазина не досчитались из-за

| | Что было | Что сделано |
|---|---|---|
| 1.7a | Любая ошибка фетча рвала обход целиком: HTTP 500 на 29-й странице из 114 → doctorhead взял 812 из 3 548; `ReadTimeout` на 2-й AJAX-странице → stoprobotvinyl взял 96 из 8 956 | `PageErrorBudget` + `BaseStoreParser.fetch_page`: страница ретраится ещё раз через 5 c (поверх трёх попыток в http_client), при неудаче пропускается. Рвём обход по `max_consecutive=3` подряд или по доле пропусков >5% — [base.py](../../Backend/app/services/scrapers/base.py) |
| 1.7b | `scraper batch done: {'ok': 7, 'failed': 0}` при двух магазинах с ошибкой в БД: `_one()` считал успехом всё, что не бросило исключение, а `crawl_store` их гасит внутри | `crawl_store` возвращает `status` (`ok`/`failed`/`blocked`/`needs_browser`), батч судит по нему и логирует `failed_stores` списком — [scraper_tasks.py](../../Backend/app/tasks/scraper_tasks.py) |

**Побочный эффект, ночь 08-12.** Терпеливый ретрай породил новый класс отказа:
stoprobotvinyl отвечал ~10 минут на одну AJAX-страницу, сессия БД простояла без
запросов, соединение умерло → `store` протух → `store.id` внутри цикла ушёл в
ленивую перечитку → `MissingGreenlet` на каждом из 8 956 листингов
(`upserted: 0, errors: 8957`). Лечение: `store.id` читается один раз до цикла,
дальше в обходе только скаляр; `_mark_error` пишет `UPDATE` по id вместо
мутации ORM-атрибута; отсечка `_CRAWL_MAX_CONSECUTIVE_ERRORS = 20`.
Общее правило: **в долгом обходе нельзя трогать ORM-объект** — только скаляры,
снятые заранее.

**Потолки времени (08-12).** Тот же инцидент вскрыл, что у обхода не было
верхней границы вообще. Добавлены два независимых потолка, оба на парсере:

| атрибут | значение | что ловит |
|---|---|---|
| `page_deadline_sec` | 120 с | зависшую страницу: таймаут клиента 90 с перемножался с ретраями и второй попыткой (~10 мин на страницу) |
| `max_crawl_seconds` | 3600 с | обход, который не падает, а ползёт — проверка стоит в цикле |

Запас к замерам четырёхкратный: самый долгий обход — skifmusic (688 страниц,
~15 мин), самая тяжёлая страница — plastinka (200 карточек, 317 KB, секунды).
`http_client` намеренно не тронут, поэтому `parse_listing`, `refresh_urls` и
разбор sitemap работают как раньше. В `counters` добавлен `elapsed_sec` —
потолки настраиваются по фактам, а не на глаз.

Цена: при HTTP 429 клиент спит по `Retry-After` (до 300 с), и дедлайн такую
паузу оборвёт. Осознанно — за 72 ч логов ни одного 429/503, а token bucket
(0.5 req/s) и так не даёт долбить магазин.

Компромисс осознанный: пропуск страницы — это молчаливая потеря ~30–200
позиций. Прикрыт тремя способами — предупреждение в лог на каждый пропуск,
`log_summary()` в конце обхода и `_SMOKE_MIN_COVERAGE = 0.5`, который не даст
проставить `last_successful_scrape_at`, если пропусков набралось много.

## 7. Definition of Done

- [ ] Ни один активный магазин не тратит > 1500 запросов на суточный цикл.
- [ ] `stock_staleness_p95` < 24 ч для всех активных магазинов.
- [ ] `Store.tier` заполнен, планировщик считает бюджет из него.
- [ ] Скрипт-разведчик отрабатывает по домену за < 1 минуты.
- [ ] В маркете ≥ 20 магазинов, из них ≥ 70% Tier A.

## 8. Открытые вопросы

- Договариваться ли с магазинами о прямом фиде (партнёрка + выгрузка) — это переводит любой
  Tier C в Tier A одним письмом. Пересекается с [AFFILIATE_OUTREACH_TEMPLATE.md](AFFILIATE_OUTREACH_TEMPLATE.md).
- Нужен ли `robots.txt`-aware более мягкий rate-limit для мелких магазинов (0.5 rps может быть
  много для слабого хостинга) — сейчас ставка одна для всех.
- Что показывать в UI для магазина, чей сток объективно свежее суток — бейдж «обновлено N ч назад»
  честнее общего обещания.
