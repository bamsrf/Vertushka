1. **5.5 — справедливая очередь** (квота на магазин внутри батча). Самое

4. **WS2 (сток) и WS3 (потолок)** — не начаты, но и не горят: `stock_from_listing`

## 1. Метрика

Считаем не магазины, а **HTTP-запросы, помещающиеся в ночное окно**.

Базовая единица из кода: `rate_limit_per_sec = 0.5` у всех парсеров
([base.py:83](../../../Backend/app/services/scrapers/base.py), переопределён в каждом shop-файле)
→ **1 запрос = 2 секунды слота магазина**.

### Два уровня ограничения

**Потолок одного магазина** — 1800 запросов/час. Лимит стоит per-domain
(`http_client.configure_domain()` в [runner.py:52](../../../Backend/app/services/scrapers/runner.py)),
поэтому магазины **не отъедают квоту друг у друга**: седьмой магазин не замедляет первые шесть.

**Глобальный потолок** — `SCRAPER_CONCURRENCY = 5`
([scraper_tasks.py:40](../../../Backend/app/tasks/scraper_tasks.py)). Одновременно крутится 5 магазинов,
поэтому бюджет измеряется в **стор-часах**:

```
окно full-HTTP: 02:00 (daily_market_sync) → 05:00 (enrich_artist_data) = 3 ч
3 ч × 5 слотов = 15 стор-часов ≈ 27 000 запросов за ночь
```

Плюс дневной `incremental_market_sync` в 14:00 — окно шире, но конкурирует с живым API-трафиком.

**27 000 запросов за ночь — бюджет, который делим между магазинами.**

## 3. Главная проблема: «ежедневный сток» — не совсем правда

Наличие обновляет не crawl, а `stock_refresh_active`
([scraper_tasks.py:157](../../../Backend/app/tasks/scraper_tasks.py)):

- `per_store_limit = 200`, `interval hours=6` → **800 листингов на магазин в сутки**;
- берутся только `matched_record_id IS NOT NULL` + `status = IN_STOCK` + `requires_browser = false`.

Следствие: полный цикл проверки наличия =

| matched-листингов в магазине | цикл обновления стока |
|---|---|
| ≤ 800 | 1 день ✅ |
| 2 000 | 2.5 дня |
| 5 000 | **6+ дней** ❌ |

То есть обещание в UI выполняется только для небольших магазинов. Это надо чинить **до**
расширения списка, иначе деградирует у всех сразу.

### 3a. Что изменилось 2026-08-11 — проблема почти закрыта побочно

После WS1 все семь парсеров берут цену и наличие **прямо из карточки листинга**,
а не со страницы товара. Это отражено флагом `stock_from_listing = True` на
парсере, и `stock_refresh_active` такие магазины больше не трогает вовсе:

```python
listing_stock_slugs = {slug for slug, cls in all_parsers().items()
                       if getattr(cls, "stock_from_listing", False)}
... .where(Store.parser_class.notin_(listing_stock_slugs))
```

Наличие теперь обновляется **целиком, каждую ночь, у всех** — то есть таблица
выше описывает уже несуществующую проблему. Осталась она только для магазинов
БЕЗ `stock_from_listing`; сейчас таких активных нет.

Побочно это же вылечило инцидент 08-10, когда `stock_refresh` давал 200 ошибок
из 200: каскад `QueryCanceledError` → `PendingRollbackError` на сессии, которую
никто не откатывал. Добавлена и отсечка по 10 ошибкам подряд.

**WS2 ниже остаётся актуальным только частично** — п. 2.1 (пропорциональный
лимит) потерял смысл, п. 2.3 (метрика staleness) частично закрыт сводкой
здоровья из WS5.4.

## 4. Стратегия отбора: чек-лист на 10 минут

Проверять по порядку, останавливаться на первом «да». **Размер каталога почти не важен —
важен способ доступа.**

1. **YML / Yandex-Market фид** — `/yandex_market.xml`, `/yml.xml`, `/export/`.
   Весь каталог с ценой и наличием одним файлом. У Bitrix-магазинов есть почти всегда. Джекпот.
2. **JSON-каталог CMS** — Tilda (`/store/api/…`), InSales, Shopify (`/products.json`). Как `found`.
3. **AJAX-эндпоинт пагинации** — открыть каталог, посмотреть Network при скролле. Как `stoprobotvinyl`.
4. **Листинг-страницы, где в карточке есть цена И наличие** — 5000 SKU при 48 на страницу
   = **~100 запросов** вместо 5000.
5. **Только sitemap + страница на товар** — дорого. Брать, если каталог < 3000 и магазин ценный.
6. **`requires_browser`** — самый дорогой класс (weekly full). Максимум 2–3 штуки, только за
   уникальный сток.

### 4′. Скрипт-разведчик (WS4.1, с 2026-08-24)

Первую половину чек-листа теперь делает скрипт — 3–7 вежливых запросов,
паспорт кандидата за ~10 секунд:

```bash
cd Backend && python -m app.scripts.scout_store <domain>
# python -m app.scripts.scout_store long-play.ru
```

Что проверяет: robots.txt (отдельно подсвечивает `/*PAGEN`, широкий `/*?*`
и запрет каталога), CMS по маркерам главной (Bitrix / Tilda / InSales /
Shop-Script / Shopify), для Tilda — живость store-API (`total > 0`, урок
domkultury; store-блок ищется и на подстраницах из sitemap — урок found,
у которого витрина на `/vinyl`), YML-фиды и `/products.json` с детектом
soft-404 (урок newartstore), sitemap с паттернами путей. Печатает tier
доступа, оценку размера (sitemap-размер всегда с пометкой «ненадёжно»),
обходные параметры, дисквалификаторы, вердикт-подсказку и готовую строку
для таблицы §7b. В БД ничего не пишет.

Что скрипт **не заменяет**: чек-лист разбираемости §4a (штрихкод, артист
отдельным полем, `image_url`) и осмотр листинга руками — вердикт ✅ значит
только «дешёвый машинный доступ есть», 🟡 — «нужен ручной осмотр», 🔴 —
причина в паспорте. Чистые функции разбора покрыты
`tests/test_scout_store.py` без сети.

### 4a. Второй чек-лист: разбираемость (с 2026-08-12 он главнее первого)

После WS1 обход перестал быть узким местом: 7 магазинов = 23 минуты из 3-часового
окна и ~1 050 запросов из 27 000 (3.9%). Новый магазин упирается не в «успеем ли
обойти», а в **«успеем ли разобрать»** — он разом вываливает весь каталог в
очередь матчинга.

**Пропускная способность матчинга (замеры 12.08).** До WS5.3 — 3.0 c на позицию
(батч из 100 занял 302 c), после — **1.26 c** (125.7 c). Возможная пропускная
способность ~2 850 позиций/час, но фактическая упирается в конфиг:
`batch_size=2000` раз в час, то есть **2 000/час и ~48 000/сутки**. Раньше батч
на 2 000 не укладывался в часовой интервал (~100 минут) и APScheduler с
`max_instances=1` пропускал следующий запуск; теперь занимает ~42 минуты.
Остаток расхода — ожидание Discogs API (rate limit 60/min).

Поэтому к чек-листу доступа добавляется чек-лист данных:

1. **Штрихкод или каталожный номер** — прямое попадание без перебора. Дороже
   всего стоит их отсутствие, а не размер каталога.
2. **Ссылка на Discogs** — редкость, но это лучший случай из возможных.
3. **Артист отдельным полем**, а не строкой «Артист – Альбом (цветной винил)».
   Разбор строки — источник ошибок (`A-ha` → artist=`A`, инцидент plastinka).
4. **`image_url` в карточке** — обязателен. В дампе Discogs обложек нет вообще
   (у нас закрыто 13%, и только добором через API), а магазинная картинка
   бесплатна и закрывает обложку всему каталогу. См. слой 5 в
   [COVERS_RATE_LIMIT_STRATEGY.md](../covers/COVERS_RATE_LIMIT_STRATEGY.md).

**Осторожно с текущими процентами сматченности.** На 12.08 они такие:
plastinka 96.8%, doctorhead 78.6%, found 30.4%, korobkavinyla 29.5%,
stoprobotvinyl 23.0%, skifmusic 20.7%, rotaryrecords 0%. Сравнивать по ним
качество данных магазинов **нельзя**: очередь матчинга была сломана (см. WS5), и
цифра отражает прежде всего, кто дольше в ней простоял. Честная картина будет
через неделю после 12.08, когда очередь один раз пройдёт всех.

### 4b. Порядок подключения

Добавлять **по одному** и дожидаться, пока `queue_left` в логах матчера вернётся
к фоновому уровню. Магазин на 20 000 позиций — это ~10 часов первичного разбора (2 000/час);
два сразу означают почти сутки, в течение которых новинки остальных магазинов
ждут. NB: новый магазин встаёт в КОНЕЦ очереди непробованных (внутри них
порядок по `first_seen_at`), поэтому его каталог разбирается последним — см.
5.5 про справедливую очередь.

**Предусловие ко всему расширению:** починить нечёткий поиск по дампу (WS5.3).
Пока он отваливается по таймауту на частых артистах, каждый новый магазин платит
квотой Discogs за релизы, которые уже лежат в нашем дампе.

## 5. Тиринг и ёмкость

Раздаём магазинам **бюджет запросов в сутки**, а не место в списке.

| Tier | Стоимость/сутки | Ёмкость | Что ограничивает |
|---|---|---|---|
| **A** — фид / JSON / AJAX | 1–100 запросов | **30–50** | матчинг и БД, не сеть |
| **B** — листинг-страницы | 100–1000 запросов | **10–15** | ночное окно |
| **C** — страница на товар | тысячи | **3–5** | ночное окно, целиком |
| **D** — `requires_browser` | weekly full | **2–3** | CPU браузерного пула |

**Было (до WS1):** 10–15 магазинов при перекосе в Tier C.

**Стало (12.08):** по обходу — 40–60, перекос устранён, все семь магазинов
Tier A/B. Но считать теперь надо не по обходу:

| ресурс | потолок | тратим | запас |
|---|---|---|---|
| запросы к магазинам за ночь | ~27 000 | ~1 050 | 25× |
| ночное окно | 3 часа | 23 минуты | 8× |
| **матчинг** | **~48 000 позиций/сутки** | весь каталог нового магазина за раз | **вот здесь тесно** |

Реальный лимит теперь — сколько **новых позиций в сутки** мы способны разобрать.
Магазин на 20 000 занимает матчер на ~10 часов; отсюда правило «по одному».

**Как чинили 5.3.** Порог перебора 0.4 вместо дефолтных 0.3, через `SET LOCAL`
(а не session-level `set_limit()` — иначе протечёт через пул соединений).
Это доказуемая граница, а не подбор: принимаем score >= 1.4 из двух similarity
по 1.0 максимум, значит каждое поле обязано быть >= 0.4. Кандидат ниже не мог
быть принят никогда. Замер: 60.9 c → 20.7 c, таймаутов нет; матчер 3.0 → 1.26 c
на позицию.

**Отвергнутая гипотеза (важно, чтобы не повторяли).** Пробовали заменить два
`%` на склейку `artist || ' ' || title` с отдельным GIN-индексом. Оказалось
**в 2 раза медленнее** на обычных запросах: Pink Floyd 1.89 → 3.64 c,
Architects 1.27 → 2.12 c. Длинная строка точнее, но триграмм у неё больше, и
GIN обходит их дольше — выигрыш в селективности съедается. Индекс на 1.5 ГБ
удалён с прода; `tests/test_dump_fuzzy_lookup.py` сторожит от рецидива.

**Правило принятия не тронуто:** score по-прежнему считается из двух отдельных
`similarity` и принимается от 1.4. Порог 0.4 сужает перебор, а не решает, кого
принять. Это сторожит `tests/test_dump_fuzzy_lookup.py` — включая проверку, что
фильтр остаётся ШИРЕ правила принятия (иначе начнём терять настоящие
совпадения) и что склейка не вернулась.

Индексы `ix_dri_artist_trgm` / `ix_dri_title_trgm` — рабочие, по ним же ходят
`rematch_store_native.py` и поиск в records API.

**Что осталось от правила приоритета.** 5.3 и 5.4 были предусловием к
расширению — оба закрыты 12.08, дорога открыта. Открытым остался 5.5:
подключать магазины можно, но новый каталог разбирается последним, поэтому
делаем **по одному** и ждём, пока `queue_left` вернётся к фоновому уровню.

**Побочное наблюдение 12.08.** После расшивки очереди матчинг за день создал
тысячи новых записей, и добор обложек (300/час) за этим не поспевает: сводка
показывает 3 565 записей, которым обложку можно поставить бесплатно. Не поломка
— просто лимит рассчитан на ровный поток, а не на всплеск. Если такие всплески
станут регулярными (а при онбординге они будут), лимит стоит поднять до ~1000.

### Размер long-play: 16 000 → 2 627 → 4 453

Цифра правилась дважды, и обе правки стоит держать перед глазами — это два
разных способа ошибиться.

**Первая правка (16k → 2 627).** В прежней редакции стояло «~16k позиций,
листинги ~800 запросов». В sitemap магазина есть раздел `sitemap_iblock_14.*`
на **140 906 URL** вида `references/detail.php?ID=…` — это справочник релизов
(энциклопедия), а не товары. Кто считает размер магазина по общему числу URL
в sitemap, ошибётся в 50 раз.

**Вторая правка (2 627 → 4 453).** Живой обход 2026-08-16 дал **4 453 товара**
против 2 627 в `sitemap_iblock_4.xml`. Карта сайта отстаёт от витрины:
в разделе rock она знает 845 URL, а витрина отдаёт 971. То есть sitemap годится
как признак «где лежат товары», но не как счётчик.

**Правило на будущее:** размер каталога брать с витрины, а не из sitemap;
из sitemap — только структуру. И считать `grep -o | wc -l`, а не `grep -c`:
карты сайта приходят одной строкой, и `-c` вернёт 1.

### long-play: почему обход стоит 16 запросов, а не 130

Плановые ~130 запросов (`PAGEN_1`, 20 шт/стр) **не подошли: `Disallow: /*PAGEN`
стоит в robots.txt**, а мы его уважаем. Штатный путь doctorhead'а здесь закрыт.

Выручил параметр `?count=N` — размер выдачи раздела, robots его не запрещает
(и сам магазин ставит `count=20` в своих фильтрах). `?count=2000` отдаёт раздел
целиком: самый большой, rock, — 971 товар, ~1 МБ, 9 c. `SIZEN_1` и `SHOWALL_1`
магазин игнорирует, `count` — единственный рабочий.

Итог: **1 запрос на `/catalog/` + 15 на разделы = 16 запросов, 47 секунд на
весь магазин.** Самый дешёвый обход в маркете (был rotaryrecords с 24).

Разделы не захардкожены — берутся со страницы `/catalog/`. Sitemap для этого
не годится ещё и по именам: в нём `non-music`, на сайте `non_music`.

Страховка от роста: если раздел перерастёт `count=2000`, в ответе появится
пагинатор — парсер это видит и повторяет запрос с удвоенным `count`. Молча
отдать первые N нельзя: обход выглядел бы успешным, а хвост каталога ушёл бы
в `daily_retire_vanished_listings` как «пропавший».

### Что несёт карточка листинга long-play

Витрина отдаёт **две панели в одном ответе** — плитку (`#display-cells`) и
список (`#display-list`), переключаются на клиенте. Плитка беднее; разбираем
список. Замер на живом обходе (4 453 товара):

| поле | покрытие |
|---|---|
| артист (отдельным полем, не резать title) | 100% |
| название, цена | 100% |
| **состояние** (`Very Good Plus (VG+)`, `Near Mint (NM or M-)`, `Mint (M)`) | **100%** |
| лейбл, жанр | 100% |
| обложка | 99.0% |
| формат | 99.1% |

Состояние прямо в листинге — редкость, и здесь оно ещё и **по-экземплярное**
(б/у магазин, грейды дискогсовские), а не константа магазина, как у
rotaryrecords. Распределение: VG+ 2 292, NM 900, M 646, VG 545, G+ 54, G 14.

Формат в листинге усечён до первого токена дискогсовской строки: у большинства
это просто «Vinyl» (на странице товара — «Vinyl, LP, Album, Reissue»), то есть
LP от 7″/12″ по листингу не отличить. У 40 товаров (0.9%) в слоте стоит
дескриптор, а не носитель («Album», «Lathe Cut», «Compilation») — там формат
оставляем пустым: матчер штрафует несовпадение формата, и ложный LP хуже
отсутствующего.

**Чего в листинге нет: года и каталожного номера.** Оба лежат на странице
товара вместе со страной, состоянием конверта и полным форматом — и каталожный
номер там дискогсовского вида (`COL 472808 1`), то есть для матчинга это
заметно ценнее artist+title. Но 4 453 страницы товара — это ~2.5 часа при
0.5 rps, что не влезает в часовой потолок обхода. `parse_listing` написан и
покрыт тестами, в ночном обходе не участвует; подключение — WS5.6 ниже.

Наличия отдельным полем нет: магазин б/у, экземпляры уникальны, ушедшее
пропадает из выдачи (как rotaryrecords) — ловит
`daily_retire_vanished_listings` по `last_seen_at`.

### domkultury.store — отклонён, парсить нечего

Магазин попал в шорт-лист по двум признакам, оба оказались неверны.

**Он не московский.** На сайте четыре упоминания Ижевска и адрес «ул. Ленина,
44а»; Москва не упоминается ни разу. В подборку он попал по ошибке — мою.

**Онлайн-каталога у него нет.** Tilda-store-блок на сайте ровно один
(страница `/indeeex`, `t_store_init('452019122')`, `storepart '928019163388'`),
и он пустой:

- store-API принимает эти параметры (не отвечает `Wrong storepartuid`) и
  возвращает `total: 0, products: []` — при этом честно отдаёт список
  жанров-`parts`, то есть магазин в Tilda заведён, но товары не залиты;
- в браузере страница не делает ни одного запроса к `store.tildaapi.com`
  и рендерит 25 скелетов-прелоадеров вместо карточек;
- на остальных страницах (`/vinylrecord`, `/market`, `/top10`) store-блока нет
  вообще.

Сайт прямо приглашает прийти ногами: «Сейчас в магазине более 6000 пластинок.
Приходите!». 6 000 — это полки, а не витрина.

**Вывод:** подключать нечего до тех пор, пока магазин не выложит каталог
онлайн. Кандидат для [AFFILIATE_OUTREACH_TEMPLATE.md](AFFILIATE_OUTREACH_TEMPLATE.md),
а не для парсера.

**Урок для чек-листа §4:** «CMS = Tilda» ещё не значит «есть каталог».
Прежде чем считать стоимость обхода, надо убедиться, что store-API отдаёт
`total > 0` — это один запрос, и он экономит весь остальной разбор.

## 9. WS7 — CPU-бюджет: расти без апгрейда железа (2026-09-04)

> **Задача раздела:** цель — наращивать дневную аудиторию и число магазинов
> (9 → 20), апгрейд CPU исключён по бюджету. Здесь — замер, диагноз и
> ранжированный план, как удержать оба роста на текущих 2 vCPU.

### Замер (метрики `~/metrics/resources.csv`, ночь 04.09)

| фаза | время (UTC) | CPU (2 ядра) |
|---|---|---|
| день/вечер, маркет спит | 19:00–02:00 | **3–8%** |
| ночной обход 9 магазинов | 02:00–02:38 | 55–62% |
| пост-обработка (матчер+обложки+инвалидация) | 02:40–05:40+ | **~70%, пики 92–99%**, load1 до 2.16 |

**Диагноз.** Плато — не «редкие дорогие запросы», а рабочий цикл: матчер
2 000 позиций × 1.26 c ≈ 42 мин из каждого часа (и так круглые сутки — фаза
hourly-джобы случайна), плюс добор обложек (PIL: до двух полных
decode→blurhash→resize→encode на файл, 1000/час), плюс инвалидация офферов —
**полный Redis SCAN на каждую из ~31.5k записей** за прогон. Сам обход —
дешёвая часть (~50 CPU-мин/ночь, из них парсинг HTML всего 3–6 мин).
Ночью это безвредно (DAU ≈ 0); опасность — когда вырастет дневной трафик:
ежечасный матчер и «инкрементальный» обход в 14:00 конкурируют с живым API.

Три структурных находки:
1. **«Инкремент» в 14:00 — второй полный обход**: `crawl_incremental` никем
   не переопределён (base.py:327 → crawl_full). Вся нагрузка ×2 каждый день.
2. **Безусловный upsert**: обход переписывает все ~66k строк (updated_at,
   raw_payload) при реально изменившихся единицах процентов → WAL, автовакуум,
   окна уведомлений и инвалидации «вбирают весь маркет».
3. **Ни у одного контейнера нет CPU-приоритетов** (compose: только mem_limit)
   — фон и API равноправны и на уровне ОС, и внутри Postgres (scheduler может
   занять 30 из 60 соединений БД).

### План: три эшелона

**Эшелон 1 — защита API (сделать до роста DAU, всё S):**

| # | мера | эффект | файл |
|---|---|---|---|
| 1.1 | `cpu_shares: 256` на scheduler в compose (api/db остаются 1024) — фон уступает под нагрузкой, ночью берёт всё. Требует только recreate (deploy делает всегда) | API получает CPU первым всегда | docker-compose.prod.yml |
| 1.2 | Отдельный пул БД для scheduler: `DB_POOL_SIZE=5, DB_MAX_OVERFLOW=5` через env (database.py параметризовать) — кап параллелизма фона внутри Postgres | фон не съедает соединения/CPU БД у API | database.py + compose |
| 1.3 | hourly-джобы: interval → cron с фиксированной минутой + jitter=90 у минутных бэкфиллов — фазы перестают быть случайными | предсказуемые окна | main.py |

**Эшелон 2 — срезать сам объём работы (главные CPU-победы):**

| # | мера | эффект | риск | усилие |
|---|---|---|---|---|
| 2.1 | **Условный upsert**: `ON CONFLICT DO UPDATE ... WHERE excluded.* IS DISTINCT FROM ...`; `last_seen_at` бампать раз в 12 ч (retire хватает) | −60k версий строк/обход ×2; окна уведомлений/инвалидации сжимаются до реальных изменений; −20–40% плато каскадно | M: RETURNING-семантика (prev-CTE), тесты notifications/retire | M |
| 2.2 | **Инвалидация офферов без per-record SCAN**: версионный ключ (INCR) вместо удаления, O(1) на запись | ~31.5k полных сканов Redis → 31.5k INCR, дважды в сутки | S | S–M |
| 2.3 | **Exact-lookup по норм. (artist,title) в дампе ДО fuzzy**: generated-колонки + btree; fuzzy остаётся фолбэком | каждая точная пара −99% CPU своей позиции; замерить долю exact-hit заранее (SQL в отчёте ревью) | 0 для match rate | M |
| 2.4 | Сортировка батча матчера по artist + батч-кэш пар (artist,title) | локальность shared_buffers; дубли пар проходят каскад один раз | 0 | S/M |
| 2.5 | Exponential backoff хроническим неудачникам матчинга: 7→14→28→56 дн (`match_attempts`) | steady-state объём fuzzy ↓ в разы; ретраи — самая дорогая категория (доходят до дна каскада) | ~0 (rematch-джобы подстрахуют) | M |
| 2.6 | `SET LOCAL jit=off, work_mem='64MB'` в транзакции fuzzy (рядом с существующим SET LOCAL) | −5–15% на тяжёлых артистах (lossy bitmap, JIT-компиляция) | 0 | S |

### Чего НЕ делать (проверено и отвергнуто)

- **uvicorn workers=2** — CLIP-модель резидентна в каждом воркере: 2×685MB
  против mem_limit 1000m = OOM (инцидент 07-10); разблокирует только вынос
  CLIP (CLIP_OUT_OF_API.md).
- **Дробление батча матчера (500×15мин)** — duty cycle не меняется, плато
  уберут только меры эшелона 2.
- **cpus:-лимит вместо shares** — режет и ночную мощность (окно растянется
  против цели 20 магазинов); допустим лишь как страховка поверх shares.
- **SoupStrainer/selectolax в парсерах** — 2–4 CPU-мин/ночь, в шуме.
- **Склейка artist||title** — закрыто WS5.3, в 2 раза медленнее, сторожится
  тестом.
- **nice/cpuset/renice pg-backend** — хрупко или теряет ночную мощность;
  cpu_shares делает то же чище.
- **Батчинг коммитов обхода** — риск повторения инцидента 07-10 ради единиц
  CPU-минут; только если после эшелона 2 обход станет узким местом.

### Правило приёмки

Каждая мера эшелона 2 внедряется с замером ДО (SQL/EXPLAIN из отчётов ревью
04.09) и сверкой плато по `~/metrics/resources.csv` ночь-к-ночи. Цель WS7:
ночное плато ≤ 50% при 9 магазинах (запас ×2 на рост до 20), дневные часы
≤ 15% фона в любой 5-минутке.
